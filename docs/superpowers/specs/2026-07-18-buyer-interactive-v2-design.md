# 買房方向診斷 C 版設計規格

日期：2026-07-18  
狀態：已確認，待使用者審閱書面規格

## 1. 目標

建立一個與現行網站完全隔離的 C 版買房互動診斷，兼顧完成率、需求精準度與台南小魏的顧問品牌感。

新版要達成：

- 將現有最多 11 步縮短為 6 個核心問題加 1 個結果／聯絡頁。
- 將 EP.01～EP.07 的買房觀念融入必要問題、條件追問與結果清單，而不是機械式增加 7 道必答題。
- 產生可執行的找房方向、預算提醒與看屋檢查清單。
- 將新名單送到獨立的 Google 試算表與 Apps Script，不影響舊版資料。
- 在手機與桌面上都呈現精緻、快速、可信任的互動體驗。

> **裁定 B（2026-07-18）：** 流程固定為 6 個核心問題頁加 1 個結果／聯絡頁。第三房用途仍是唯一會依答案改變核心問題內容的條件追問；若使用者在第 6 頁選擇「其他」避開條件，僅於 priorities 頁內 inline 顯示「其他避開條件」說明欄。此欄不是額外問題頁，不得增加第 7 個問題頁。

## 2. 不在本次範圍

- 不修改或覆蓋現行 `real-estate-buyer-interactive` 專案、網址、Google Apps Script 或試算表。
- 不建立會員系統、登入功能或後台 CRM。
- 不串接房仲物件資料庫做即時配對。
- 不根據區域或地址捏造行情、價格、貸款成數或物件資訊。
- 不要求使用者回答職業、年齡、婚姻狀態等非必要個人資料。

## 4. 視覺方向

採用已選定的「C｜顧問式互動卡」。

設計語言：

- 主色為深墨綠、暖米白與少量金色，延續房產顧問的穩定感與台南在地溫度。
- 每次只聚焦一個決策主題，使用大型標題、短提示、清楚選項與明確進度。
- 「小魏提醒」以低干擾資訊卡出現，傳達影片觀念，但不阻斷作答。
- 手機以單欄卡片為主；桌面使用居中的主卡加精簡結果預覽，不再保留過長的右側資訊欄。
- 動畫只用於進場、選項確認與結果生成，並支援 `prefers-reduced-motion`。
- 使用真正的繁體中文排版，避免過多裝飾圖示、過密表情符號與制式紫色漸層。

## 5. 問題流程

### 第 1 題：購屋目的與時程

同一頁完成兩個高度相關的選擇：

- 購屋目的：自住、換屋、婚房、幫家人找、投資／置產、先了解行情。
- 預計時程：1 個月內、3 個月內、半年內、一年內、先看看。

用途：判斷服務節奏與名單溫度，不再分成兩個獨立步驟。

### 第 2 題：生活區域

- 想找區域：提供台南常用區域快捷選項，並保留自由輸入。
- 生活重心：工作通勤、學校接送、家人照顧、日常採買、無固定地點。

用途：不只收集行政區，也理解實際生活動線。此題融入 EP.03「看屋不只看室內」的觀念。

### 第 3 題：舒服的購屋負擔

- 可準備自備款：區間選擇，可選「還不確定」。
- 每月可舒服負擔的房貸：區間選擇，可選「希望小魏協助試算」。

用途：以前端規則估算可討論的總價方向，但明確標示為初步整理，不是銀行核貸承諾。此題融入 EP.01 與 EP.05。

### 第 4 題：實際空間需求

- 平常居住人數。
- 希望房數：1～2 房、2 房、3 房、3 房以上、還不確定。
- 若選 3 房或以上，才出現條件追問：「第三個房間準備拿來做什麼？」選項為家人長住、工作／書房、兒童房、偶爾來客、還沒想好。

用途：用真實生活用途判斷空間，不為房數而房數。此題直接融入 EP.07。

### 第 5 題：物件必要條件

在同一頁用分組選項收集：

- 物件類型：電梯大樓、華廈／公寓、透天、電梯透天、其他。
- 屋齡接受度：10 年內、20 年內、30 年內、不拘。
- 車位需求：一定要平車、車位即可、有最好、不需要。

用途：合併現行物件類型、屋齡與車位三個步驟。商用店面、廠房、土地若需要，透過「其他」填寫，不讓一般住宅買方看到過多無關選項。

### 第 6 題：不能妥協與一定避開

- 最重視條件最多選 3 個：地點、格局、採光通風、安靜、管理、屋況、生活機能、停車、價格。
- 一定避開可選填：西曬、頂樓、特殊風水／路沖、基地台或高壓電、格局問題、無特殊忌諱、其他。

題目提示使用：「裝潢可以改，但地點、格局與每天的生活方式更值得先確認。」融入 EP.02 與 EP.04。

### 第 7 頁：結果與聯絡

- 先顯示回答摘要與結果預覽。
- 收集稱呼、台灣手機號碼及明確同意聯繫勾選。
- 成功送出後顯示完整買房方向卡、預算提醒、看屋清單及 LINE 聯絡按鈕。
- LINE 使用正式連結 `https://line.me/R/ti/p/%40tainanwei`。
- 聯絡區塊顯示：魏泉承、永慶不動產-小東南紡店、0927-617-207。

## 6. EP.01～EP.07 的呈現方式

| 影片 | 新版使用位置 | 呈現方式 |
| --- | --- | --- |
| EP.01 買房第一步，不是先看房？ | 第 3 題 | 先問舒服月付與自備款，再談總價方向 |
| EP.02 房子漂亮就能買嗎？ | 第 6 題 | 強調裝潢可改，格局與生活需求優先 |
| EP.03 看完房子，先別急著走 | 第 2 題、結果清單 | 收集生活重心，提醒走訪室外與生活圈 |
| EP.04 第一間就喜歡，可以買嗎？ | 結果清單 | 提供「心動後再確認」決策檢查項目 |
| EP.05 房子便宜，為什麼不能急？ | 第 3 題、結果提醒 | 將修繕、管理費與生活餘裕列入負擔提醒 |
| EP.06 白天看過，晚上還要來？ | 結果清單 | 建議晚間再訪，檢查照明、車流、停車與社區進出 |
| EP.07 你真的需要三房嗎？ | 第 4 題 | 三房以上才詢問第三房用途 |

完整結果中的「影片七問」會以可勾選的看屋檢查清單呈現，不增加必答步驟：

1. 每月房貸負擔後，生活還能保留餘裕嗎？
2. 拿掉裝潢加分後，格局仍符合每天的使用方式嗎？
3. 室外環境、通勤與生活圈實際走過了嗎？
4. 第一眼心動後，價格與必要條件也確認了嗎？
5. 加上修繕、管理費與持有成本後，總負擔仍合適嗎？
6. 白天與晚上都看過周邊環境嗎？
7. 每一個房間都有明確用途嗎？

## 7. 結果邏輯

前端依答案產生三層結果：

1. 找房方向：區域、用途、時程與物件條件的摘要。
2. 預算提醒：自備款、月付舒適度與需保留的生活／修繕餘裕；不顯示保證核貸或精確銀行額度。
3. 看屋策略：從影片七問中挑出最相關的 3～5 項，再附完整清單。

買方狀態只使用中性名稱：

- 方向探索中。
- 條件整理中。
- 可以開始精準比較。

不使用會讓客戶感到被評分、被拒絕或被貼標籤的名稱。

## 8. 前端結構與資料流

前端維持無框架的靜態 HTML、CSS、JavaScript，避免為單頁工具增加不必要的建置依賴。

建議內部模組：

- `questionConfig`：題目、選項、驗證與條件顯示。
- `state`：使用者答案與目前步驟。
- `renderQuestion()`：只負責畫面渲染。
- `validateStep()`：只負責當前步驟驗證。
- `deriveResult()`：從答案產生人格、方向、預算提醒與清單。
- `buildPayload()`：建立送往 Apps Script 的固定資料格式。
- `submitLead()`：處理送出、重試、成功與失敗狀態。

資料流：

1. 使用者作答，答案只暫存於瀏覽器記憶體。
2. 每一步即時驗證並更新簡短的「小魏提醒」。
3. 最後一頁顯示摘要，使用者填寫稱呼、手機並勾選同意。
4. 前端建立結果與 payload，再送往獨立 Apps Script。
5. Apps Script 驗證必要欄位、寫入獨立試算表並回傳 JSON。
6. 前端收到成功訊號後顯示完整方向卡與聯絡行動。

## 9. 試算表欄位

獨立試算表至少包含：

- 建立時間
- 來源版本
- 稱呼
- 手機號碼
- 購屋目的
- 購屋時程
- 想找區域
- 生活重心
- 自備款區間
- 舒服月付區間
- 居住人數
- 希望房數
- 第三房用途
- 物件類型
- 屋齡接受度
- 車位需求
- 最重視條件
- 一定避開條件
- 買方狀態
- 找房方向摘要
- 預算提醒
- 看屋策略
- 同意聯繫

不儲存 IP、精確裝置識別碼或與服務無關的敏感資料。

## 10. 驗證與錯誤處理

- 自由輸入內容在前端輸出時必須逸出，Apps Script 寫入試算表前也要轉為文字，避免 HTML 注入或公式注入。
- 手機接受 `09xxxxxxxx`，顯示時保留使用者易讀格式，送出時正規化為 10 碼數字。
- 條件追問未顯示時，其舊答案必須清空，避免送出不可見資料。
- 送出按鈕在請求期間鎖定，避免重複名單。
- 送出失敗時保留全部答案，顯示重新送出、複製需求摘要與 LINE 聯絡三種出口。
- 結果推導永遠提供保守預設值，不因選填題空白而崩潰。
- Apps Script 回傳一致的 `{ ok, message, submissionId }` 格式；錯誤不向使用者暴露內部堆疊或試算表資訊。

## 11. 可用性與無障礙

- 主要互動元素至少 44 × 44 CSS 像素。
- 可使用鍵盤完成全部流程，焦點樣式清楚。
- 顏色對比符合 WCAG AA 的一般文字要求。
- 錯誤訊息同時使用文字與 `aria-live`，不只靠顏色。
- 手機寬度 360px 不產生水平捲動。
- 使用者可回上一步修改，且不丟失後續仍有效的答案。

## 12. 驗證與驗收標準

### 程式檢查

- HTML 結構與 JavaScript 語法檢查通過。
- 桌面與手機的所有 6 題流程都可完成。
- 三房條件追問只在 3 房或以上出現，改選後答案會清空。
- 所有結果分支都能產生非空的方向、提醒與看屋清單。
- 錯誤手機不能送出；正確手機可以送出。

### 後端與資料檢查

- 使用測試資料送出後，重新讀取獨立試算表的精確新增列，確認每個欄位對應正確。
- 模擬 Apps Script 錯誤與網路失敗，確認答案保留且重試／複製／LINE 出口可用。
- 連續點擊送出不會建立重複列。

### 視覺與發布檢查

- 以瀏覽器檢查 360px 手機、768px 平板與一般桌面寬度。
- 檢查首頁、每一題、條件追問、錯誤狀態、送出中、成功結果與失敗結果。
- GitHub Pages 部署完成後，實際開啟正式網址並重新跑一次主要流程。
- 舊版正式網址在新版發布後仍可正常使用且內容未改變。

## 13. 完成定義

只有在下列條件都成立時，C 版才算完成：

- 新版位於獨立 GitHub 專案與獨立 Pages 網址。
- 舊版檔案、網址與資料後端均未改動。
- 新版 6 題加 1 結果頁可完整使用。
- EP.01～EP.07 的七個核心觀念都出現在必要問題或結果清單。
- 新版資料成功寫入獨立試算表且欄位經重新讀取驗證。
- 手機、桌面、錯誤處理、LINE 連結與聯絡資訊均已實際驗證。
